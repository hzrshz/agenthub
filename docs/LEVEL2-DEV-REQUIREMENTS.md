# 等保二级应用系统开发要求（等保 2.0 · GB/T 22239-2019 第二级）

> 用途：本仓库及后续应用系统开发、评审、发布须遵循的安全基线。开发人员按「开发落地要求」实现，评审/CI 按「验证方式」把关，测评时按「测评证据」提供材料。
>
> 依据：GB/T 22239-2019《信息安全技术 网络安全等级保护基本要求》（第二级安全通用要求）、GB/T 28448-2019《等级保护测评要求》、公安部《网络安全等级保护测评高风险判定实施指引（试行）》（具体文号以公安部发布为准）、GM/T 0054《信息系统密码应用基本要求》（密评）。
>
> **精度声明**：安全计算环境各控制点的"等保要求（二级）"为贴合应用系统开发视角的归纳表述，正式测评结论以 GB/T 22239-2019 / GB/T 28448-2019 现行有效文本为准。条目编号统一按二级安全通用要求 8.1.4（安全计算环境）、8.1.9（安全建设管理）口径描述。

---

## 0. 等保二级的基本认识

1. **定位**：二级系统指"受到破坏后会对公民、法人和其他组织的合法权益造成严重损害，但不涉及国家安全、社会秩序和公共利益"的定级对象。定级要素为"业务信息受到破坏时所侵害的客体 + 侵害程度"。
2. **测评流程**：定级 → 备案 → 测评 → 整改 → 监督检查。测评结论综合得分 ≥ 70 分且**不存在未整改的高风险项**才算基本通过（优 ≥90 / 良 80–89 / 中 70–79 / 差 <70）。
3. **对应用系统的意义**：测评对象不仅看网络、主机，**应用系统和数据（安全计算环境）是核心测评对象**，其中身份鉴别、访问控制、安全审计、数据有效性校验是失分和判高风险的集中区。
4. **三级才会强制出现**的项（提前规划可加分，二级不扣分）：两种及以上组合鉴别技术（双因素，三级 9.1.4.1 d）、可信验证（启动度量）、异地实时备份/热冗余、存储侧数据保密性的强制要求、敏感标记等。**验证码不是任何一级的测评项**——防自动化爆破看的是"登录失败处理"机制效果，不是具体控件。
5. **密评关系**：等保二级本身不强制国密算法；但若同步做商用密码应用安全性评估（GM/T 0054），密码应用（身份鉴别、传输/存储保密性与完整性、密钥管理）需使用经批准的密码技术，国密 SM2/SM3/SM4 是主推方向（详见第 5 节）。

## 1. 安全计算环境 · 应用和数据（技术控制点，二级）

### 1.1 身份鉴别（M）

| 等保要求（二级） | 开发落地要求 | 验证方式 / 测评证据 |
|---|---|---|
| a. 登录用户身份标识唯一，鉴别信息有复杂度要求并定期更换 | 用户标识全局唯一（不可复用）；口令策略：最小长度（建议 ≥8，含大小写/数字/特殊字符至少三类）、禁止与用户名/常见弱口令相同、定期强制更换（建议 90 天）、防历史口令复用 | 口令策略配置文档；自动化正则/强度校验单测；弱口令字典覆盖用例 |
| b. 登录失败处理：结束会话、限制非法登录次数、登录超时自动退出 | 登录失败锁定（如连续 5 次失败锁定 15 分钟）；服务端会话/令牌空闲超时自动失效（建议 ≤30 分钟）；所有登录入口（含管理端、API）统一走失败处理 | 失败锁定与解锁的单测；超时失效的集成测试；锁定策略配置项可查 |
| c. 远程管理时鉴别信息防窃听 | 全站强制 HTTPS/TLS（≥TLS 1.2），登录/鉴权接口禁止明文 HTTP；HSTS 建议显式开启与否按部署拓扑决定（已有反向代理时与代理同值）；Cookie 标记 HttpOnly、Secure、SameSite | `make check` 中 TLS 配置校验；抓包/日志确认无明文口令传输 |
> 关于"双因素/验证码"：两种及以上组合鉴别技术（口令+OTP/证书/生物特征等）是**三级**要求（9.1.4.1 d），二级身份鉴别仅 a)-c) 三条；验证码不是二级（也不是任何一级）的测评项——GB/T 22239-2019 全文没有"验证码"字样，防爆破看 b) 的"限制非法登录次数"是否落实。若未来升三级，需补第二鉴别因子。

> 红线段：**口令明文存储、无任何复杂度校验、默认口令未修改且可登录 → 高风险**（详见 §3）。

### 1.2 访问控制（M）

| 等保要求（二级） | 开发落地要求 | 验证方式 / 测评证据 |
|---|---|---|
| a. 授权主体配置访问控制策略，规定主体对客体的访问规则 | 显式授权模型（RBAC + 数据级归属校验），**默认拒绝**；未声明即不可访问；所有资源访问须经授权判定，不依赖前端隐藏 | 越权用例：未登录/低权限/他人资源三组用例全部 403/404；代码评审无"裸查库"路径 |
| b. 不同账户最小权限、相互制约 | 角色权限最小化：普通用户/管理员/审计角色分离；敏感操作（删除、导出、改口令、改权限）单独授权或二次确认；密钥等机密仅服务端持有 | 权限矩阵文档；角色切换后的功能清单测试 |
| c. 重命名或删除默认账户、修改默认口令 | 产品交付不留默认口令；初始化账户强制首次登录改密；后台管理入口不暴露弱默认凭据 | 交付检查表；部署文档确认无默认凭据 |

**d. 及时删除/停用多余过期账户，避免共享账户**

- **开发落地要求**：提供账号停用/删除能力；会话与令牌随账号禁用即时失效；禁用用户不得通过存量会话/令牌继续访问；不允许"共用账号"模式（一个账号多人使用）。
- **验证方式/证据**：账号禁用即时性测试（禁用后旧会话、旧 Token、配对码全部失效——AgentHub 的"用户禁用即时生效"即为此类）；停用账号清单可审计。

### 1.3 安全审计（M）

| 等保要求（二级） | 开发落地要求 | 验证方式 / 测评证据 |
|---|---|---|
| a. 审计覆盖每个用户，审计重要用户行为和重要安全事件 | 记录登录成败、登录失败、权限变更、账号变更、敏感操作（删除/导出/配置修改/口令重置）、异常访问；审计绑定到具体用户而非 IP | 审计事件清单文档；关键路径均有点审计埋点（代码评审） |
| b. 审计记录字段完整（时间、用户、事件类型、结果、来源等） | 记录：时间戳、用户标识、来源 IP、节点标识（如适用）、操作对象、操作类型、结果（成功/失败）、错误码、耗时；时间统一 UTC+偏移或本地时区并注明 | 日志样例截图/文档；结构与字段单测 |
| c. 审计记录受保护、定期备份、防未预期删除/修改/覆盖 | 审计日志仅追加；管理端用户无删除日志权限（审计管理员与业务管理员分离）；日志轮转与归档；**审计日志本身不记录敏感明文**（仅元数据） | 权限测试：普通/管理角色均不能改删审计日志；备份/归档脚本存在 |

### 1.4 入侵防范（应用相关部分，M）

| 等保要求（二级） | 开发落地要求 | 验证方式 / 测评证据 |
|---|---|---|
| a. 最小安装原则 | 镜像/打包只含运行必需组件；不安装编译器、调试器、冗余工具；容器以最低权限用户运行 | Dockerfile/部署清单评审；镜像扫描 |
| d. 数据有效性校验：人机/通信接口输入符合设定要求 | 所有外部输入（HTTP 参数、JSON 体、文件上传、节点上报数据）服务端校验：类型/长度/取值范围/格式/枚举；参数化查询或 ORM 防 SQL 注入；输出编码防 XSS；上传白名单（扩展名+内容嗅探+大小限制+独立存储目录）；对代理协议输入（WebSocket 上报）同样校验 | 安全测试：SQL 注入、XSS、上传绕过用例全红；SAST/DAST 扫描无高危；输入校验单测 |
| e. 发现已知漏洞并及时修补 | 上线前依赖漏洞扫描清零（Go module / npm / 基础镜像 CVE）；发布流程含漏洞扫描门禁；建立漏洞响应与升级闭环 | CI 扫描报告；依赖版本固定 + SBOM 清单 |

### 1.5 恶意代码防范（R）

- **等保要求（二级）**：安装防恶意代码软件或等效功能，定期升级恶意代码库。
- **开发落地要求**：容器/主机侧部署防病毒或运行时扫描；**应用侧配合**：不内置可执行载荷、不动态拼装执行脚本、下载物校验（长度/哈希/类型）、上传文件做内容级检测（对上传目录定期扫描）。
- **验证方式/证据**：上传/下载文件的校验测试；部署文档含防病毒配置。

### 1.6 数据完整性（M）

- **等保要求（二级）**：采用校验技术或密码技术保证**重要数据**（鉴别数据、重要业务数据、重要审计数据、重要配置数据）在**传输过程**与**存储过程**中的完整性。
- **开发落地要求**：
  - 传输：TLS ≥1.2 提供传输完整性；对无 TLS 的站点内部链路用消息认证（HMAC）兜底。
  - 存储：重要配置/审计数据存哈希或 MAC；可校验数据库不一致（如关键记录加校验和或依赖事务约束）；备份文件提供完整性校验（如 sha256 清单）。
- **验证方式/证据**：TLS 配置校验；存储完整性检测用例；备份校验和脚本。

### 1.7 数据保密性（M）

- **等保要求（二级）**：采用密码技术保证鉴别数据、重要业务数据在**传输过程**中的保密性（存储侧保密性为三级强制项，**建议一并落实**）。
- **开发落地要求**：
  - 传输层强制（已含于 1.1c）：cookie/令牌/认证头只走 HTTPS。
  - 存储层（建议）：机密（Token、密钥、数据库口令）加密存储或引用托管密钥；数据库敏感字段（个人信息）可列级加密。
- **验证方式/证据**：无明文凭据落库（代码评审+库文件权限 0600 佐证）；加密配置文档；漏洞扫描无"弱加密/明文传输"告警。

### 1.8 数据备份恢复（M）

- **等保要求（二级）**：提供本地数据备份与恢复功能（备份数据建议异地/场外存放；异地实时备份与热冗余为三级）。
- **开发落地要求**：应用数据与配置可备份、可恢复；备份含数据库与应用配置；提供恢复演练脚本并定期执行；备份文件访问受控（权限 0600/0700）。
- **验证方式/证据**：备份/恢复脚本；演练记录（时间、结果）——测评常抽查恢复演练记录。

### 1.9 剩余信息保护（M）

- **等保要求（二级）**：鉴别信息所在存储空间、存有敏感数据的存储空间（文件目录、数据库记录）在释放或再分配前完全清除。
- **开发落地要求**：
  - 密码/令牌明文变量用后清零（不落日志、不落调试输出）；日志与审计记录不得含口令、Token 明文、参数值。
  - 删除功能做真实删除或加密覆写/软删+定期清理，不留可恢复明文；临时文件、上传缓存定期清除；测试数据脱敏，禁止真实敏感数据流入开发/测试环境。
- **验证方式/证据**：日志样例检索口令/Token 为 0 命中；删除后数据不可复原的测试；临时目录清理任务存在。

### 1.10 个人信息保护（M）

- **等保要求（二级）**：仅采集和保存业务必需的用户个人信息；禁止未授权访问和非法使用。
- **开发落地要求**：
  - 最小收集：字段清单即数据字典，无业务需要不采集（不含"顺手多存"）；个人信息导出/删除（含注销后清除）提供能力。
  - 访问控制：个人信息接口纳入 1.2 的授权与数据归属校验；日志不落个人信息全文（脱敏）。
  - 告知同意：若有对外收集，提供隐私说明（管理侧配合）。
- **验证方式/证据**：数据字典文档；越权读个人信息的用例全红；日志脱敏样例。

## 3. 高风险判定红线（开发侧必拦截项）

依据《网络安全等级保护测评高风险判定实施指引（试行）》，以下场景**一旦存在即可能判高风险（"一票否决"）**，任何发布不得携带：

| # | 红线场景 | 开发强制要求 | 拦截手段 |
|---|---|---|---|
| 1 | 口令明文/弱哈希存储 | 口令只存 argon2id（或加盐强哈希）；禁止 MD5/SHA1 无盐；禁止口令写入日志/配置/代码 | 代码评审 + 扫描（Gitleaks/自定义规则）+ 单测 |
| 2 | 无口令复杂度校验 | 登录/注册/改密统一走强度校验（长度+字符类+弱口令黑名单） | 策略集中配置（internal/config），核心路径复用 |
| 3 | 默认口令可登录 | 交付无默认口令；首次登录强制改密；初始化账户需显式设置 | 安装/初始化流程检查；交付检查表 |
| 4 | SQL 注入 / XSS / 文件上传漏洞 | 参数化查询；输出编码；上传白名单+内容校验+隔离存储 | SAST/DAST 高危清零；渗透用例回归 |
| 5 | 越权访问（水平/垂直） | 服务端对每个资源做归属校验（跨租户返回 NotFound，不泄露存在性）；角色权限最小化 | 越权用例集（未登录/低权限/他人资源）纳入回归 |
| 6 | 鉴别信息明文传输 | 全站 TLS ≥1.2；登录/认证接口拒绝明文 | 网关/应用 TLS 校验；抓包确认 |
| 7 | 认证缺失直连管理/数据接口 | 所有管理接口与数据接口默认需鉴权；白名单式放行 | 路由层统一鉴权中间件，无裸路由 |

> 本仓库既是开发代码也是测评对象，红线项已落实的范例见 §6。

## 4. 安全开发生命周期（SDL）落地机制

后续应用系统开发按以下阶段嵌入等保要求，每个阶段有产物可供测评举证：

1. **需求/设计**：新增功能列表对照 §1 控制点做一次"合规影响"勾选；识别新采集的个人信息；确定数据流（哪些数据进入日志/存储/第三方）。
2. **编码**：遵循安全编码基线——服务端校验一切输入、输出编码、参数化查询、机密不落日志、错误信息不含内部细节（不泄露栈/路径/版本细节给客户端，但内部日志保留上下文）；机密（Token/密钥）不进仓库（`gitignore` + 密钥管理）。
3. **依赖与供应链**：固定依赖版本；每次合并前跑依赖漏洞扫描；维护 SBOM；第三方组件评估（对应 §2 软件采购）。
4. **测试门禁**：
   - `make check`（单测+静态检查+构建）为常规前置；
   - 发布前：SAST + 依赖扫描清零 + 越权/注入/XSS 回归 + 会话失效用例；
   - 有交互式 UI 时补一次人工安全走查（登录、口令找回、管理端、上传）。
5. **发布**：发布前确认——默认凭据无残留、调试开关关闭、`web_dist` 产物与源码一致（本仓库 CI 有漂移即红）、漏洞扫描报告附发布记录。
6. **运维反馈**：漏洞报告响应闭环（评估→修复→回归→记录）；口令策略、锁定阈值、日志保留期等常量集中在 internal/config 且不可运行时弱化。

## 5. 云环境与密评扩展（视部署形态）

- **云端部署（等保云计算扩展要求）**：多租户数据隔离（本仓库按 owner_user_id 分区、跨租户一律 NotFound 即为直接落地）；虚拟机/容器间网络隔离；数据残留清理（对应 §1.9）；管理接口与租户接口分离并受控。
- **商用密码应用（GM/T 0054）**：身份鉴别、传输/存储保密性与完整性、密钥管理四类密码应用功能。等级保护二级**不强制国密**，但密评与信创政务场景趋向 SM2/SM3/SM4；若规划国密，需在架构层预留可替换算法与密钥管理位（见 README「国密现状说明」），避免事后改造困难。
